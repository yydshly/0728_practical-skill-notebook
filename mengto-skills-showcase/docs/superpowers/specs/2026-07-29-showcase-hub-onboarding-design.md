# 统一产品能力展厅与中文新手引导设计

日期：2026-07-29

状态：优化版书面规格已确认；需求基线冻结，实施结果以分层验证记录为准

目标受众：非技术客户、管理者与第一次访问者

## 1. 背景与问题

现有套件已经包含三款由 MengTo Skill 工作流形成的可运行产品，但用户进入任意产品后，无法快速回答：

1. 这个产品是什么；
2. 应该如何体验；
3. 它适用于什么业务；
4. 三款产品为什么同时存在；
5. Skill 与最终产品是什么关系。

根因不是产品功能不足，而是缺少统一入口、参观路线、产品内任务说明、Skill 到产品的映射，以及返回展厅的导航。

本次改动不增加第四款产品，也不重做三款产品的核心体验。它新增一个中文优先的能力展厅，并为三款产品补齐一致的新手引导。

仓库中另外两项既有演示——雾屿灯塔与 Typographic Flags——继续独立运行，但不属于本次三产品能力展厅。README 和展厅必须统一使用“能力展厅三产品”这一范围，避免“五项作品”和“三款产品”混为一谈。

## 2. 已确认的产品方向

采用“产品能力展厅”方案：

- 第一屏直接解释这不是一款包含三个关卡的游戏，而是三款互补产品；
- 三张产品卡先用短信息帮助扫读，详细任务、Skill 能力和更多场景放入说明对话框；
- 用户可以先看说明，也可以直接进入体验；
- 产品第一次打开时显示中文任务引导；
- 每个产品始终可以重新打开说明并返回展厅；
- 首页用一句故事线串联三款产品：“同一套专业 Skill，如何产出三种完全不同的可运行产品。”

未采用的方向：

- 纯故事化长页：叙事更强，但查找单个产品较慢；
- 开发者控制台：技术信息充分，但第一次访问者负担过高。

## 3. 设计契约

```text
Entry mode: Revision-led
Request revision: 2
Target user and context: 非技术客户、管理者与第一次访问者；不了解 Three.js、Skill 或当前目录结构
Desired first impression: 这是一个可信、可体验、易理解的三产品能力展，而不是三个缺乏关联的技术 Demo
Visual ambition: Editorial
Experience architecture: Editorial Flow（展厅）+ 保留现有产品的 Spatial Stage / Hybrid Workspace
Visual constraints: 中文优先；暗色专业基调；真实产品截图；高对比正文；三产品使用独立强调色；不依赖 WebGL 才能理解
Information constraints: 第一屏使用固定的正向定位文案；卡片默认层只保留一句话作用、适合业务、体验时间和两个操作；详细能力默认折叠；英文 Skill 名称不是主叙事

Primary journey: 进入展厅 → 以 30 秒内完成首次扫读为设计目标 → 选择产品 → 阅读中文任务 → 完成一个小成功点 → 返回展厅

Autonomy authorization: 用户先后确认目标受众、产品能力展厅方案、首页结构、三产品引导、视觉技术结构和验收标准，并要求继续

Observable completion criteria: 自动化证明文案、路线和操作可达；至少一名首次访客在不阅读 README 的情况下能用自己的话说明三产品作用及 Skill 与成品关系；用户可完成每款产品定义的小成功点、重新查看说明并返回对应产品卡
Coverage record: 见第 10 节
```

## 4. 信息架构

### 4.1 展厅首页

页面按以下顺序组织：

1. **首屏定位**
   - 眉题：“MengTo Skills 产品能力展”
   - 主标题：“这是三款独立、可实际操作的 3D 产品体验”
   - 说明：“它们不是同一款游戏的三个关卡，而是资产工具、动作游戏和商品配置器。Skill 是指导 Codex 开发与验收的专业工作说明，最终交付仍是普通网页产品。”
   - 主操作：“查看三款产品”，滚动到 `#products`
   - 次操作：“这些产品是怎样做出来的”，滚动到 `#how-it-works`

2. **三款产品卡**
   - 默认层只显示产品名称、一句话作用、适合的业务、预计体验时间；
   - “先看说明”与“进入体验”。

3. **业务选择指南**
   - 管理和验收 3D 资产 → Monster Forge；
   - 制作可玩的互动内容 → Ashfall Arena；
   - 展示和配置复杂商品 → Mech Atelier。

4. **这些产品是怎样做出来的**
   - 使用四步语义流程：
     `选择业务目标 → Codex 读取相关专业工作说明 → 开发与测试 → 交付普通网页产品`
   - 在本段首次显示对应英文术语：“这些专业工作说明在 Codex 中称为 Skill。”
   - 明确 Skill 不会被浏览器加载，也不是运行时插件。
   - 英文 Skill 清单放入展开详情，不占据默认阅读路径。

5. **验证与边界**
   - 默认展示非技术结论；
   - 技术测试数量、GPU、设备和真人门槛放入可展开详情；
   - 不把自动测试写成真人可用性证明。

### 4.2 产品说明预览

“先看说明”打开语义化对话框，不离开展厅。内容包括：

- 产品作用；
- 三步体验任务；
- 典型商业场景；
- 主要 Skill 能力组；
- 预计体验时间；
- “进入体验”与“关闭”。

Escape 关闭，关闭后焦点返回原按钮。

### 4.3 产品卡固定内容与小成功点

| 产品 | 默认层一句话作用 | 适合的业务 | 预计体验时间 | 说明层补充 | 本轮机器可观察的小成功点 |
| --- | --- | --- | --- | --- | --- |
| Monster Forge | 在同一工作台检查怪物模型、动作和技术叠加 | 游戏资产库、角色编辑器、数字资产验收 | 2–3 分钟 | 三步任务、资产审阅能力组、可迁移场景 | 选择另一个怪物并成功切换一项技术叠加 |
| Ashfall Arena | 直接体验战斗、敌人 AI、成长和反馈组成的动作游戏切片 | 游戏原型、互动营销、战斗系统验证 | 3–5 分钟了解核心操作；完整首次挑战仍按 8–12 分钟人工门槛 | 操作说明、战斗能力组、完整挑战边界 | 关闭引导后产生真实移动与攻击事件；不要求本轮完成 Boss |
| Mech Atelier | 更换机甲部件并立即看到 3D 外观与参数变化 | 汽车选配、工业设备、家具和定制商品 | 3–5 分钟 | 三步任务、配置能力组、概念价格边界 | 更换一个部件并观察摘要参数和分享 URL 同步变化 |

默认卡片不显示完整三步任务、Skill 组或多条商业场景，避免形成三张文档墙；这些内容只在“先看说明”中展开。

## 5. 三产品新手引导

### 5.1 Monster Forge

**作用：** 检查和管理 3D 怪物资产。

**任务：**

1. 选择一个怪物；
2. 切换动作、骨骼或碰撞体；
3. 查看模型来源与技术参数。

**意义：** 减少游戏资产验收、沟通和返工成本。

### 5.2 Ashfall Arena

**作用：** 展示完整动作游戏系统。

**任务：**

1. 学会移动、攻击、闪避和格挡；
2. 完成普通敌人与精英战；
3. 选择升级并挑战 Boss。

**意义：** 快速验证战斗手感、AI、关卡和移动端体验。

**特殊约束：**

- 使用独立的 `guideGateOpen` 运行门禁，不写入或切换游戏自身的 `state.paused`；
- 首访门禁在第一个 `requestAnimationFrame` 与第一次输入采样前建立；
- 门禁打开时清空已有输入，不推进 fixed-step 模拟、音频时钟或表现时钟；场景只允许渲染冻结的可读背景；
- “开始体验”、关闭按钮和 Escape 都只把 `guideGateOpen` 从真变为假；游戏是否继续推进仍完全由玩家暂停、升级、失败和完成状态决定；
- 释放门禁不会解除玩家原本的暂停，也不会改变升级、失败、完成、存档或输入状态；
- “返回能力展厅”直接离开当前页面，不先恢复模拟；
- 玩家暂停、升级、失败或完成对话框打开时，不允许再叠加第二个引导对话框；
- 自动打开因已有产品对话框被拒绝时，不能标记为已关闭；宿主在阻塞状态结束后可以再次调用 `open()`；
- 重复打开和关闭引导不得重复注册监听器、重置游戏或写入存档；
- 页面销毁时清理引导门禁与监听器，但不调用普通关闭/恢复分支，也不伪造一次恢复帧。

### 5.3 Mech Atelier

**作用：** 配置和展示复杂 3D 商品。

**任务：**

1. 更换机体、装甲和武器；
2. 查看负载、火力、防御和兼容性变化；
3. 使用拆解视图、分享配置或导出海报。

**意义：** 可迁移到汽车、工业设备、家具和定制商品销售。

### 5.4 统一引导行为

三个产品统一提供：

- 首次访问自动显示中文引导；
- “这是什么？”按钮可重新打开；
- “返回能力展厅”链接；
- “不再自动显示”选项；
- 存储不可用时仍可正常打开、关闭和重新查看；
- 桌面键鼠与移动触摸说明；
- 可见焦点、Escape 关闭和焦点返回；
- reduced-motion 下取消非必要入场动画。

引导不得遮蔽永久恢复路径；即使用户选择不再自动显示，“这是什么？”按钮仍保留。

引导状态使用版本化、按产品隔离的键：

```text
mengto-showcase:guide:<product-id>:v<guide-version>:auto-hidden
```

三个产品首次接入均使用版本 `1`。

状态规则：

- 单纯关闭、点击“开始体验”或按 Escape，只关闭当前页面会话；
- 只有用户勾选“不再自动显示”后再关闭，才写入 `auto-hidden=true`；
- 三款产品的键互不影响；
- 引导内容发生实质变化时提升版本号，旧版本偏好不会阻止新版说明出现；
- 存储 getter、读取或写入失败时，只在内存中记住当前页面会话的关闭；刷新后重新自动显示；
- 任何持久状态都不影响“这是什么？”按钮手动重开。

跨产品导航统一使用当前标签页，不打开新窗口。产品入口的展厅返回地址包含对应锚点：

```text
/#product-monster-forge
/#product-ashfall-arena
/#product-mech-atelier
```

返回后浏览器定位到对应产品卡；展厅只在识别到三个合法产品锚点时，把焦点移到该卡可聚焦的标题（`tabindex="-1"`），并用 `preventScroll` 避免第二次跳动。普通首页访问和其他锚点不得被强制改焦点。直接访问产品时仍显示返回展厅入口。产品现有存档或 URL 状态继续由产品自己维护，展厅不承担跨应用状态保存。

## 6. 视觉方向

### 6.1 总体风格

- 保留现有暗色、专业、沉浸式产品气质；
- 展厅背景和正文亮度高于三款产品，优先解决深色小字可读性；
- 不用 emoji、CSS 伪图、占位框或手工 SVG 冒充产品资产；
- 使用三款产品的真实验收截图作为产品卡主视觉；
- 首页核心意义不依赖截图、Canvas 或 WebGL 才能读取。

### 6.2 产品识别

| 产品 | 强调色 | 视觉含义 |
| --- | --- | --- |
| Monster Forge | 暖橙 | 资产、锻造、检查 |
| Ashfall Arena | 灰烬红 | 战斗、风险、反馈 |
| Mech Atelier | 冷青 | 精密、配置、工业 |

颜色不作为唯一识别方式，产品名称、图像替代文本和文字标签必须同时存在。

### 6.3 响应式

- 桌面：三张卡并列，首屏可见定位和开始参观入口；
- 平板：两列或单列，产品说明对话框不超出视口；
- 390px 手机：单列卡片，说明使用底部面板或全宽对话框；
- 320px 宽度不得出现横向滚动；
- 所有主要触控目标至少为 44×44 CSS px；
- 移动前景层使用 `100dvh` 与 `env(safe-area-inset-*)`，不遮挡关闭和返回操作；
- 浏览器放大到 200% 时，主旅程仍可操作且内容不被固定高度裁切；
- 现有产品的空间场景和移动面板结构保持不变，引导作为前景层接入。

说明层优先使用原生 `<dialog>`；必须具备可读名称与描述关联、`aria-modal` 语义、背景不可聚焦、打开时滚动锁定、对话框内焦点循环，以及关闭后的焦点恢复。移动底部表现只是视觉变化，不降低同一语义和键盘行为。

### 6.4 动效

- 只用轻量进入、展开和焦点反馈解释状态变化；
- 不使用持续漂浮或装饰性视差；
- `prefers-reduced-motion: reduce` 时立即切换状态，不使用位移动画。

## 7. 技术结构

### 7.1 新增展厅应用

新增工作区：

```text
apps/showcase-hub
```

职责：

- 渲染展厅首页；
- 维护三产品说明内容与业务映射；
- 打开产品说明对话框；
- 根据环境解析三产品 URL；
- 不导入 Three.js，不依赖 WebGL。

默认开发端口：`4172`。

### 7.2 共享引导包

新增工作区：

```text
packages/showcase-guide
```

建议公开接口：

```ts
type ProductGuideConfig = {
  productId: "monster-forge" | "ashfall-arena" | "mech-atelier";
  guideVersion: number;
  title: string;
  purpose: string;
  steps: readonly string[];
  meaning: string;
  desktopControls: readonly string[];
  touchControls: readonly string[];
  hubHref: string;
  canOpen?: () => boolean;
  onOpen?: () => void;
  onClose?: (reason: "start" | "dismiss" | "escape") => void;
};

type ProductGuideController = {
  open(): boolean;
  close(reason?: "dismiss" | "escape"): void;
  destroy(): void;
  isOpen(): boolean;
};

function createProductGuide(
  host: HTMLElement,
  config: ProductGuideConfig,
): ProductGuideController;
```

模块职责：

- 创建语义化说明对话框和持久入口；
- 安全读取和写入“不再自动显示”偏好；
- 在 `localStorage` getter、读取或写入失败时退化为当前会话行为；
- 管理焦点、Escape、背景交互和销毁；
- 使用 `guideVersion` 生成按产品隔离的状态键；
- 使用 `canOpen` 防止与已有产品对话框叠加；
- 暴露带关闭原因的 `onOpen` / `onClose`，由 Ashfall 控制独立引导门禁；
- 提供共享样式，但通过语义变量允许三个产品继承自身强调色。

`guideVersion` 必须是正整数。`open()` 只有在控制器未销毁、当前未打开且 `canOpen` 未拒绝时才返回 `true` 并触发一次 `onOpen`；其他情况返回 `false`，不改变会话或持久状态。内部“开始体验”使用 `start` 原因，关闭按钮使用 `dismiss`，Escape 使用 `escape`，每次成功关闭只触发一次 `onClose`。返回展厅使用普通同标签页链接；若复选框已勾选，可以先安全写入偏好，但不经过 `onClose` 的恢复分支。`destroy()` 移除 DOM 与监听器并使后续方法成为无操作，不触发 `onClose`；Ashfall 的应用级销毁顺序固定为先停止 RAF、输入和音频，再销毁引导并清理门禁，因此不会产生恢复帧。

它不读取 Vite 环境变量，也不管理游戏状态、商品配置、Three.js 场景或产品路由。`hubHref` 必须由宿主应用解析并传入。

### 7.3 产品 URL

地址策略必须区分开发与生产。

开发默认值只在 `import.meta.env.DEV` 为真时生效：

| 产品 | URL |
| --- | --- |
| 展厅 | `http://127.0.0.1:4172/` |
| Monster Forge | `http://127.0.0.1:4173/` |
| Ashfall Arena | `http://127.0.0.1:4174/` |
| Mech Atelier | `http://127.0.0.1:4175/` |

生产构建绝不回退到 `127.0.0.1`，默认使用同域路径：

| 入口 | 生产默认值 |
| --- | --- |
| 展厅 → Monster Forge | `/monster-forge/` |
| 展厅 → Ashfall Arena | `/ashfall-arena/` |
| 展厅 → Mech Atelier | `/mech-atelier/` |
| 三产品 → 展厅 | `/` 加对应 `#product-*` 锚点 |

宿主可以通过明确的 Vite 构建变量覆盖这些路径：

| 宿主 | 构建变量 |
| --- | --- |
| 展厅资源基址 | `VITE_APP_BASE` |
| 展厅的三个产品链接 | `VITE_MONSTER_FORGE_URL`、`VITE_ASHFALL_ARENA_URL`、`VITE_MECH_ATELIER_URL` |
| 三产品的展厅返回链接 | `VITE_SHOWCASE_HUB_URL`，由各产品补上自身固定锚点 |

地址解析优先级固定为：

```text
显式构建变量 → 生产同域路径（PROD）或固定回环地址（DEV）
```

共享引导包只接收解析完成的 `hubHref`。生产构建测试必须扫描四个产物，确认没有意外的 `127.0.0.1`、`localhost` 或 `[::1]`，并验证往返链接不含 `target="_blank"`、使用同一标签页和正确锚点。

为验证同域路径而不承诺公开部署，新增本地组合产物：

```text
dist/showcase/
  index.html
  monster-forge/
  ashfall-arena/
  mech-atelier/
```

`npm run build:showcase` 为四个应用传入 `VITE_APP_BASE=./`；展厅链接覆盖为 `./monster-forge/`、`./ashfall-arena/`、`./mech-atelier/`，产品的展厅链接覆盖为 `../` 后再附加自身锚点。这样组合目录既可从本地域名根路径预览，也可整体放入任意子路径。`npm run test:showcase-preview` 在一个本地源站下验证展厅 → 产品 → 对应产品卡的完整往返。公开托管与 CDN 仍不在本次范围。

### 7.4 一条命令运行

新增：

```text
scripts/dev-showcase.mjs
```

根脚本：

```json
"dev": "node scripts/dev-showcase.mjs",
"dev:hub": "npm run dev --workspace @showcase/hub",
"build:showcase": "node scripts/build-showcase.mjs",
"test:showcase-preview": "playwright test --config playwright.showcase-preview.config.ts"
```

`npm run dev` 的行为契约：

1. 启动前检查 4172–4175，任一端口占用即指出产品与端口并返回非零；
2. 并发启动四个 Vite 子进程；
3. 对四个固定地址轮询 HTTP，使用单一 20 秒总截止时间；就绪定义为入口 GET 返回 `200–399`，且响应正文包含该应用的固定识别标记；
4. 只有四个地址都达到就绪定义后，才打印一次“全部可访问”和产品名称、可点击地址；
5. 任一子进程启动失败、就绪超时或运行中异常退出时，终止整个进程树并返回非零；
6. Windows 的 Ctrl+C、Ctrl+Break 与正常退出都必须清理四个子进程，不能遗留 Vite 服务。

四个入口分别提供 `<meta name="showcase-app">`，`content` 固定为 `showcase-hub`、`monster-forge`、`ashfall-arena` 和 `mech-atelier`；就绪检查不得把端口上返回的任意成功网页误判为目标产品。

启动脚本集成测试覆盖：成功就绪、端口占用、就绪超时、子进程崩溃和用户中断。测试使用伪子进程与临时端口，不占用真实 4172–4175。

现有 `dev:forge`、`dev:arena`、`dev:atelier` 保留。

## 9. 错误与回退

- 展厅本身不使用 WebGL；图片加载失败时，卡片文字和操作仍完整；
- 产品链接使用正常锚点，不引入客户端路由依赖；
- 说明存储失败不阻止引导使用，只是不记住“不再自动显示”；
- 开发地址缺失时使用固定回环地址；生产地址缺失时使用明确的同域路径，任何生产产物出现意外回环地址都使测试失败；
- 统一启动脚本遇到端口占用时明确指出产品和端口，不静默改用未知端口；
- Ashfall 引导打开期间使用独立门禁停止模拟，不切换 `state.paused`，也不使用只遮罩画面的伪暂停；
- 关闭或销毁引导后清理事件监听器，并恢复触发按钮焦点。

## 11. 实施拆分

实施计划必须拆成六个可独立验收阶段，每阶段遵循失败测试 → 最小实现 → 全绿 → 候选提交 → 独立复审：

1. **内容、URL 契约与共享引导**
   - 完成两层产品内容、版本化存储、无障碍对话框和 DEV/PROD 地址解析；
2. **统一展厅**
   - 完成首页、说明层、真实预览图、桌面/移动/键盘/reduced-motion；
3. **Monster 与 Mech 接入**
   - 完成两个低风险产品的首访、重开、返回和小成功点；
4. **Ashfall 独立门禁接入**
   - 单独处理首帧、输入、音频、表现时钟与已有游戏状态组合，不与通用 UI 改动混交；
5. **统一启动与组合生产预览**
   - 完成四服务就绪/清理、同域产物与往返验证；
6. **文档与全量终验**
   - 更新四份产品验证、套件验证和 README，执行全部工程与浏览器门禁。

前一阶段的公开接口和复审结论是后一阶段的输入；不得在多个阶段同时改写 Ashfall 主循环或启动脚本。

## 12. 测试策略

### 12.1 单元与契约

- 产品内容模型包含名称、作用、任务、能力、商业场景、时间与 URL；
- 共享引导的首访、会话关闭、持久隐藏、版本升级、产品隔离和安全存储；
- Escape、背景 inert、焦点循环、焦点返回和销毁；
- Ashfall 的独立引导门禁不改写 `state.paused`，也不推进模拟、音频、表现或存档；
- 启动脚本的端口预检、HTTP 就绪、超时、崩溃、中断清理和终端输出；
- 生产 URL 与组合产物不包含意外 loopback；
- README 包含非技术定位与一条命令启动。

所有新行为遵循测试先行：先看到缺少功能导致的明确失败，再写最小实现。

## 14. 技术交付与产品验证

### 14.1 技术交付完成

只有以下条件同时满足，才可以把本次工程改动标记为技术交付完成：

1. 第一屏固定文案、三产品范围和主旅程已自动验证；
2. 三产品卡默认层保持短信息结构，说明层完整回答作用、体验、能力、场景和时间；
3. 三款产品首访引导、重开和返回路径均可用；
4. Ashfall 在说明打开时不会隐形推进，也不会误解除已有暂停或产品对话框状态；
5. 一条命令可以确认固定四端口全部就绪，并在失败或中断时清理整个进程树；
6. 桌面、390px、320px、200% 放大、键盘、safe-area 和 reduced-motion 证据完整；
7. README 与实际启动方式一致；
8. 自动测试、构建、浏览器回归和差异检查通过；
9. 执行验证记录中没有 `continue`；若存在 `defer`，必须写明已尝试的替代路径、未验证风险和复验触发条件。

### 14.2 对外产品结论

以下结论不能由自动化或技术交付状态代替：

- “首次访客能在 30 秒内理解三产品及其关系”：需要至少一名非技术首次访客、不阅读 README 的计时复述记录；
- “Ashfall 的完整首次挑战适合 8–12 分钟”：继续使用现有真人首次体验门槛；
- 真实设备表现与公开部署可用性：仍在本次非目标内，不能从本地模拟或组合预览外推。

缺少上述真人或外部证据时，技术交付仍可完成，但对应产品结论必须在验证记录中保持 `defer`，不得写成“已验证”。
