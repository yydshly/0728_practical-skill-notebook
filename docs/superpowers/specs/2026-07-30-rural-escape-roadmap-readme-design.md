# 《雾村：逃离》后续路线 README 补充设计

**日期：** 2026-07-30

**状态：** 已获用户口头确认，等待书面设计审阅

**适用范围：** 仓库根 `README.md` 与 `rural-mutation-escape/README.md`

## 1. 目标

当前《雾村：逃离》已经完成研究原型 v0.1 的代码、演示、说明、验证和远端发布闭环。本轮不继续实现游戏功能，只把下一阶段可以研究的方向沉淀到两层 README，并明确这些内容尚未开始、不是当前版本能力。

文档需要同时回答：

1. 当前阶段为什么可以暂时闭环；
2. 后续可以沿哪些方向继续；
3. 推荐的研究顺序及原因；
4. 哪些内容仍是规划，不能被理解为已经实现。

## 2. 采用方案

采用“双层 README、内详外简”的方案：

- 项目内部 README 保存完整路线、优先级、目标和未实现边界；
- 根 README 只给出简短摘要并引导读者进入项目 README；
- 不复制大段内容，不新建功能清单冒充验收结果；
- 不修改运行时代码、测试、图片、音频、构建配置或来源文档。

只修改内部 README 会让仓库首页看不到项目的后续研究价值；在根 README 重复完整路线又会造成维护分叉。因此双层结构在可发现性与真实性之间更合适。

## 3. 项目 README 设计

在“已知限制”之后、“核心闭环研究文档”之前增加：

```markdown
## 后续演进建议（暂缓实施）
```

该章节首先声明：

- 当前 v0.1 已完成阶段性闭环；
- 下面是后续研究路线，不是已交付能力；
- 当前没有启动对应实现，也没有承诺发布日期。

随后记录三条路线。

### 3.1 A：补齐真正的游戏闭环

这是推荐的第一优先级。方向包括：

- 敌人的视野、听觉、遮挡与短期记忆；
- 攻击前摇、捕获与失败状态；
- 确定性检查点和可靠重试；
- 可交互南门、动态碰撞和正式通关结算；
- 完成后停机或明确的重新游玩入口。

目标不是扩大地图，而是把现有村庄做成一段可失败、可恢复、可重复游玩的 2–4 分钟垂直切片。

### 3.2 B：提升美术与体感

在核心闭环稳定后，逐步升级：

- 人物和变异体模型、骨骼与动作；
- 农村建筑、道路、植被、材质和环境细节；
- 灯光、雾效、粒子、命中或危险反馈；
- 更稳定的镜头构图和过场表现；
- 在不破坏碰撞、任务锚点和性能预算的前提下替换程序化占位资产。

该路线不应先于玩法闭环大规模展开，否则视觉资产会被尚未稳定的流程反复返工。

### 3.3 C：沉淀大模型驱动的生成流程

在地图、任务和角色接口稳定后，研究可复用的 AI 驱动流程：

- 从故事描述生成地图数据、区域、道路与地标；
- 生成 NPC、敌人、任务链、对白和触发条件；
- 由约束、schema 和确定性校验限制模型输出；
- 自动生成对应的单元测试、浏览器证据场景和验收清单；
- 记录提示词、来源、生成产物与人工审查结果。

目标是形成“故事输入 → 结构化设计 → 可运行内容 → 自动验证 → 人工审查”的开发管线，而不是让模型直接无约束修改整个游戏。

### 3.4 推荐顺序

README 明确推荐：

```text
A 游戏闭环 → B 美术体感 → C 生成流程
```

先确定可玩的规则与接口，再提升内容品质，最后把稳定接口抽象成可生成流程。三条路线可以研究，但本轮均保持“暂缓实施”状态。

## 5. 真实性边界

新增文字必须始终区分：

- **当前已实现：** 现有四步线性流程、地图、碰撞、追逐、引导、视角和音频；
- **后续规划：** 失败/重试、完整感知与捕获、动态南门、美术升级和生成管线；
- **本轮交付：** 仅 README 文档补充。

不得使用“新增”“现已支持”“已经完成”等暗示规划已落地的表述，也不写具体发布日期、版本承诺或未经验证的性能目标。
