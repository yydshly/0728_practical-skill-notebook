# 《雾村：逃离》电杆与共享实体碰撞设计

## 目标

让道路灯杆、电杆及后续同类细长实体遵守稳定的世界规则：

- 主角不能穿过实体杆体，接触时沿障碍平滑滑动；
- 追逐者使用同一套角色障碍数据，不能穿过杆体；
- 电线、横杆和绝缘子不参与人物碰撞；
- 细杆不参与第三人称镜头遮挡，避免镜头被频繁推近；
- 可见网格与碰撞体来自同一份关卡定义，避免视觉和物理状态分离。

本设计只解决共享实体碰撞和基础局部避让，不在本轮实现完整寻路、视线感知或战斗失败系统。

## 当前状态

- 玩家使用半径为 `0.42` 的圆形角色体，通过 `resolveCircleMove()` 与轴对齐矩形碰撞体进行 X/Z 分轴移动。
- `VILLAGE_LAYOUT.colliders` 只描述房屋、院墙和少量路障。
- 道路灯杆由 `addLantern()` 根据 `VILLAGE_LAYOUT.lights` 生成，但两个 `road_lantern` 条目没有碰撞定义。
- `addUtilityPole()` 可以生成电杆外观，却没有关卡数据入口或碰撞契约。
- 追逐者直接修改世界位置，不消费关卡边界或碰撞体。
- 两个现有巡逻节点位于建筑碰撞体内部；一旦追逐者开始遵守碰撞，这些节点会导致卡住。

## 方案比较

### 方案 A：关卡数据声明共享障碍（采用）

在关卡数据中明确声明矩形和圆形障碍，由视觉工厂、玩家移动、敌人移动和验证测试共同消费。

优点：

- 玩法规则不依赖具体美术网格；
- 玩家和敌人不会形成两套碰撞数据；
- 可继续复用于树干、水井、石墩和其他圆柱实体；
- 可以在不加载 Three.js 网格的情况下做确定性测试。

代价：

- 需要扩展现有碰撞结构，并重写少量关卡数据。

### 方案 B：把灯杆近似成小矩形

只在现有 `colliders` 中手工增加两个很小的矩形。

优点是改动最少；缺点是绕行手感有方角、灯杆位置会被重复维护，未来增加电杆时容易再次漏配。该方案不采用。

### 方案 C：从场景网格自动推导碰撞

运行时读取杆体的包围盒或包围球。

优点是看似自动；缺点是玩法依赖美术层级、缩放和加载顺序，导入模型后不稳定，也不利于无渲染测试。该方案不采用。

## 数据契约

碰撞体使用一个明确的联合结构：

```js
{
  id: 'road_lantern_a_body',
  shape: 'circle',
  x: -4.6,
  z: 18,
  radius: 0.16,
  blocksActors: true,
  blocksCamera: false,
}
```

矩形障碍继续使用：

```js
{
  id: 'home_body',
  shape: 'box',
  x: -12,
  z: 28,
  halfX: 5.2,
  halfZ: 4.2,
  blocksActors: true,
  blocksCamera: true,
}
```

规则如下：

- `shape` 只能是 `box` 或 `circle`；
- 所有角色障碍都必须具有稳定且唯一的 `id`；
- `box` 必须提供正数 `halfX`、`halfZ`；
- `circle` 必须提供正数 `radius`；
- 所有障碍仍位于统一的平面玩法层，碰撞只计算 X/Z；
- `blocksActors` 默认显式填写，不通过视觉类型猜测；
- `blocksCamera` 只表达镜头策略，不改变人物碰撞。

两个道路灯杆直接在相应 `lights` 定义中附带圆形碰撞配置，运行时从同一个灯光条目生成可见杆体、灯光和角色碰撞体。当前未实例化的 `addUtilityPole()` 只调整为接受同样的数据契约，不在本轮额外增加新电杆。

## 运行时结构

### 关卡构建

`createVillage()` 负责把以下来源规范化为一个共享 `actorColliders` 集合：

- 建筑和院墙矩形；
- 道具集群碰撞；
- 道路灯杆圆形碰撞；
- 后续通过同一契约加入的电杆或树干。

视觉对象不反向生成碰撞数据。碰撞和外观共享稳定 ID 与位置，但保持独立层。

### 碰撞计算

`collision.js` 提供统一的“圆形角色对障碍”判定：

- 圆形角色对矩形障碍：保留最近点距离计算；
- 圆形角色对圆形障碍：比较角色半径与障碍半径之和；
- `resolveCircleMove()` 继续使用 X/Z 分轴解析，因此接触灯杆时可以沿未受阻轴滑动；
- 未知 `shape` 不允许静默退化为其他碰撞类型，必须由关卡验证发现。

### 玩家

玩家继续以半径 `0.42` 使用 `resolveCircleMove()`。本轮不改变移动速度、输入或角色尺寸。

### 追逐者

`createPursuer()` 接收与玩家相同的 `bounds` 和 `actorColliders`：

- 追逐者采用独立但固定的角色半径；
- 每次计划位移先通过共享解析器，再写入世界位置；
- 接触杆体或建筑时使用分轴结果进行局部滑动，不允许穿透；
- 重新布置位于建筑内部的巡逻节点，并增加节点净空验证。

这能保证基本巡逻和直线追逐不会穿过实体。它不承诺在复杂建筑背后自动寻找全局最短路；完整导航网格或路径搜索属于后续敌人 AI 任务。

### 镜头

道路灯杆和细电杆的 `blocksCamera` 为 `false`，不加入 `cameraOccluders`。建筑、院墙和大型路障继续沿用现有镜头遮挡策略。

## 验证与错误处理

`validateVillageLayout()` 扩展以下检查：

- 碰撞 ID 唯一；
- `shape` 合法；
- 尺寸为有限正数；
- X/Z 坐标为有限值；
- 所有巡逻节点与角色障碍保持追逐者半径所需的净空；
- 道路灯杆的可见定义和碰撞定义共存。

无效关卡数据必须在测试和启动诊断中明确报告，不能通过读取场景网格自动补救。

## 测试设计

### 单元测试

1. 圆形角色正面移动时不能穿过圆形灯杆。
2. 斜向移动接触灯杆时，未受阻轴仍能移动，形成可读滑行。
3. 从重叠或边界状态离开障碍时不会被锁死。
4. 现有矩形碰撞行为保持不变。
5. 两个道路灯杆的碰撞体由灯光定义生成，位置与可见杆体一致。
6. 追逐者不能与灯杆、房屋或路障重叠。
7. 所有巡逻节点满足角色净空。
8. 灯杆不进入镜头遮挡集合。

### 浏览器验证

1. 主角分别从四个方向和斜向接近两个道路灯杆。
2. 主角能沿灯杆滑开并继续前往目标，不会卡住。
3. 在追逐证据状态中，让追逐者路线经过灯杆附近，确认不穿透且不与玩家重合。
4. 走完收音机、邻居、手电和南门路线，确认新障碍不造成软锁。
5. 检查桌面和窄屏画面、控制台错误、绘制调用和三角形数量没有异常回归。

## 验收标准

- 玩家无法穿过道路灯杆或后续使用同一契约的电杆；
- 玩家接触杆体时不会突然弹回或被永久卡住；
- 追逐者不能穿过任何 `blocksActors` 障碍；
- 玩家和追逐者消费同一个关卡障碍集合；
- 灯杆视觉位置与碰撞位置来自同一条关卡定义；
- 电线、绝缘子不阻挡角色；
- 细杆不推动第三人称镜头；
- 所有既有测试和新增测试通过，完整剧情路线仍可完成。
