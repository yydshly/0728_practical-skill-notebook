# Finesse 证据图谱产品设计

日期：2026-07-30
状态：交互设计已确认，书面规格等待用户复核

## 1. 背景

第八项目 `finesse-skill-product-research` 已完成固定版本的能力地图、研究协议、产品机会和未来展厅规划，但当前交付仍只有研究文档，没有可运行网页。

本规格定义下一阶段的首个可运行产品：**Finesse 证据图谱**。它把研究内容转化为一个面向产品、设计与工程负责人的中文交互展厅，让访客沿着“上游能力 → 本项目分析 → 扩展产品场景”理解 Finesse。

研究对象继续固定为：

- 上游仓库：`mouse-lin/finesse-skill`
- 固定提交：`ba004b21e14e55385992dff6e345db7108deca78`
- Skill：`finesse-ui` `0.12.0`
- 上游许可：MIT

本产品是独立研究与解释性演示，不是上游官方版本、分支或续作。

## 2. 产品目标

### 2.1 目标用户

首要用户是需要判断 Finesse 能力、证据成熟度和产品化价值的：

- 产品负责人；
- 设计负责人；
- 工程负责人。

研究人员可以继续通过证据链接深入查看固定来源，但首屏不以完整研究档案的密度组织信息。

### 2.2 核心成功标准

第一次访问的用户应能在 3 分钟内回答：

1. Finesse 已定义了哪些前端设计能力？
2. 本项目对这些能力作出了什么分析，证据处于什么状态？
3. 这些能力可以扩展成什么产品，推荐主线是什么？

### 2.3 首版原则

- 用真实可操作的页面解释能力，不只展示文字卡片。
- 每个关键声明均可追溯到固定来源、分析理由或产品假设。
- 不把本项目制作的示例称为上游原始页面。
- 不把静态规则映射或解释性演示称为实验验证。
- 不接入 AI、后端服务或实时 GitHub 数据。
- 不复制上游源码、示例图片或第三方素材。

## 3. 选择的产品方案

首版采用**三幕引导式叙事**，而不是三栏研究工作台或三个彼此独立的数字展馆。

选择理由：

- 更符合“3 分钟完成产品判断”的目标；
- 能保持“能力事实 → 分析 → 产品扩展”的因果连续性；
- 可把证据层作为随时展开的辅助信息，而不让首次访问陷入研究细节；
- 在移动端可以自然折叠为单列阅读。

展厅视觉采用**编辑型证据图谱**：米白纸张底、深墨文字、克制状态色、强排版和细线结构。更高强度的视觉表达留给被演示的 `brand` 页面，不让展厅外壳与研究内容竞争。

## 4. 真实性与状态模型

首版使用以下六种状态，状态名称必须与颜色和图标同时出现：

| 状态 | 含义 | 首版用法 |
|---|---|---|
| 上游已定义 | 固定上游提交明确写出了该机制。 | 能力事实、规则和命令。 |
| 本项目解释性演示 | 本项目依据固定规则独立制作了可操作示例。 | 三个 register 示例页面。 |
| 本项目已验证 | 已按冻结输入、原始记录和浏览器证据完成验证。 | 首版不使用该状态。 |
| 计划验证 | 研究协议存在，但实验或运行时证据尚未完成。 | B1–B5、浏览器证据和对照结论。 |
| 产品构想 | 基于能力与分析提出的产品机会。 | 六个扩展方向及推荐主线。 |
| 尚未实现 | 规格中描述但首版没有接入的能力。 | AI 生成、真实审计、持久化和团队治理。 |

现有 `SHOWCASE-PLAN.md` 使用“上游已实现”描述上游 Skill 机制。实施首版时须将该标签同步迁移为“上游已定义”，并新增“本项目解释性演示”；项目 README、展厅计划、类型化数据和界面必须使用同一套状态名称。

所有解释性示例持续显示以下边界说明：

> 本页面由本项目依据固定版本规则独立制作，用于解释能力；它不是上游原始页面，也不是已完成的受控实验。

页面不得出现没有来源或状态的性能分数、审美评分、通过率、市场数据或实验结论。

## 5. 产品信息架构

```text
研究范围与状态说明
  → 第一幕：原 Skill 能力演示
  → 第二幕：我们的分析演示
  → 第三幕：扩展产品场景
  → 后续路线与使用场景
```

顶部固定区域包含：

- 产品名称；
- 固定提交和 Skill 版本；
- 六种状态的简化图例；
- 三幕导航和阅读进度；
- “3 分钟阅读”入口；
- 研究范围说明入口。

桌面端在需要时显示右侧证据栏。移动端把证据栏折叠为底部抽屉或章节内手风琴，不保留永久三栏布局。

## 6. 第一幕：原 Skill 能力演示

### 6.1 演示方式

采用“**可操作画布 + 证据侧栏**”。

画布一次展示一个完整示例，通过 `brand`、`product`、`commerce` 标签切换；证据侧栏同步展示：

- register 与页面任务；
- Design Read；
- SOUL / SPECTACLE / DENSITY；
- 采用的规则或 reference；
- 固定上游来源；
- 适用边界；
- 当前证据状态。

### 6.2 统一虚构场景

三个示例使用同一个虚构 SaaS 产品 `Nova` 及其新功能 `Release Guard`，避免把内容差异误判为 register 差异。

#### Brand 示例

- 页面：`Release Guard` 新功能发布落地页。
- 目标：建立认知并传达产品人格。
- 主要现象：低信息密度、明确品牌语气、一个有理由的视觉引擎、非承重动效和降级路径。
- 首版交互：章节导航、功能故事展开、主要 CTA 的页面内定位。

#### Product 示例

- 页面：`Release Guard` 发布运营工作台。
- 目标：让发布负责人读取状态并定位阻塞项。
- 主要现象：高信息密度、表格/指标层级、状态筛选、清晰的读取任务。
- 首版交互：状态筛选、记录选择、详情展开和空筛选结果。

#### Commerce 示例

- 页面：`Release Guard Pro` 功能套餐选择与升级摘要。
- 目标：比较方案、理解权益和确认升级范围。
- 主要现象：信任信息、规格比较、价格/席位变化、清晰后果和反暗模式。
- 首版交互：月付/年付切换、席位调整、方案选择和本地订单摘要；不提供真实支付或提交。

三个示例共享内容身份，但组件、密度和视觉语法彼此隔离。任一示例不得承担真实业务操作。

## 7. 第二幕：我们的分析演示

### 7.1 冻结 brief

分析使用一个固定的高层业务 brief：

> Nova 将发布 Release Guard。团队需要建立新功能认知，让现有管理员查看发布风险，并允许组织评估升级方案。

### 7.2 关键分析结论

高层业务 brief 不应被强行压成一个 register。Finesse 的 register 判断以页面任务为单位，因此本项目把它拆成三个可审阅表面：

- 建立认知的发布页 → `brand`；
- 读取发布风险的工作台 → `product`；
- 评估升级方案的套餐页 → `commerce`。

这一拆分属于本项目分析，不是上游已经提供的成套 Nova 产品。

### 7.3 分析步骤

`AnalysisStepper` 依次展示：

1. 原始冻结 brief；
2. 目标用户与任务拆分；
3. 每个页面的 register 判断；
4. 三旋钮及其理由；
5. 需要加载的 references；
6. 适用边界和不确定性；
7. 来源与证据状态；
8. 可导出的只读决策包预览。

首版的“导出”只下载由静态数据生成的 JSON 或 Markdown 决策包，不调用模型，也不声称完成需求发现。

## 8. 第三幕：扩展产品场景

第三幕演示一个“SaaS 新功能发布”的产品化工作流：

```text
冻结需求
  → 页面任务拆分
  → register 与三旋钮决策包
  → 证据审计摘要
  → 产品判断与缺口
```

### 8.1 决策包

决策包汇总三个页面任务、Design Read、旋钮、references、理由、版本和状态。用户可以逐项展开，但不能在首版保存为真实项目记录。

### 8.2 证据审计摘要

审计摘要严格分开：

- 上游规则来源；
- 本项目示例中的静态实现信号；
- 首版浏览器测试证据；
- 尚未执行的受控实验；
- 人工设计判断。

浏览器测试只能证明本展厅和示例页面在被测条件下的行为，不能证明 Finesse 在所有 AI 助手或项目中产生相同结果。

### 8.3 产品判断

场景结尾给出可解释的产品判断：

- Design Brief Router 适合作为入口；
- AI Design Review Console 适合作为审计核心；
- 两者可组成“设计决策与审计工作台”的首条产品主线；
- 该判断属于产品机会排序，不是市场验证或商业承诺。

## 9. 后续扩展方向与使用场景

展厅展示六张机会卡：

1. Design Brief Router；
2. AI Design Review Console；
3. Design Model Studio；
4. Multi-Register Prototype Lab；
5. Pattern Knowledge Base；
6. Team Governance Layer。

每张卡包含：

- 目标用户；
- 使用场景；
- 继承的 Finesse 能力；
- 需要新增的产品能力；
- 最小闭环；
- 风险；
- 价值与成本；
- 优先级；
- 依赖和证据状态。

机会地图支持按优先级和状态筛选，并能回到前述能力、分析步骤或场景节点。

## 10. 技术架构

首版是 `finesse-skill-product-research/` 内的独立 Vite + React + TypeScript 应用。

### 10.1 主要模块

- `ResearchShell`：版本、状态图例、导航和阅读进度。
- `CapabilityGallery`：三个 register 示例的选择与挂载。
- `BrandDemo`：品牌发布页解释性示例。
- `ProductDemo`：发布运营工作台解释性示例。
- `CommerceDemo`：套餐选择解释性示例。
- `EvidenceRail`：来源、规则、限制和状态。
- `AnalysisStepper`：冻结 brief 的分析链。
- `ScenarioJourney`：决策包、审计摘要和产品判断。
- `OpportunityMap`：六个扩展方向。

每个模块只接收类型化数据和必要的本地交互状态。三个示例使用独立样式作用域，不能依赖彼此内部组件。

### 10.2 数据目录

静态数据至少拆分为：

- `research-meta`：固定提交、版本、许可和范围；
- `capabilities`：能力、来源、限制和状态；
- `demo-registers`：三个示例的 Design Read 与内容配置；
- `analysis-trace`：冻结 brief 和逐步判断；
- `scenario`：决策包与审计摘要；
- `opportunities`：六张机会卡；
- `status-model`：状态名称、说明和展示令牌。

数据以 TypeScript 类型和运行时断言共同约束。构建前验证固定版本、来源 URL、必填状态、能力引用和机会卡数量。

### 10.3 客户端状态

首版只保存：

- 当前章节；
- 当前 register；
- 分析步骤；
- 展开的证据；
- 场景步骤；
- 机会筛选。

状态保存在内存和 URL 中，不写入服务端。刷新后根据 URL 恢复可分享的章节、register 和步骤；无效参数回到安全默认值并显示一次说明。

### 10.4 数据流

```text
类型化静态数据
  → 构建期完整性检查
  → 章节视图模型
  → 三幕界面与证据侧栏
  → 本地选择和 URL 状态
```

运行时不请求 GitHub、模型 API、数据库或分析服务。

## 11. 视觉系统

- 背景：暖米白和浅纸张层级。
- 文字：深墨黑与中性灰。
- 强调：有限的橙色用于章节和关键动作。
- 状态：绿、黄、紫、灰等辅助色，必须配合文字和图标。
- 字体角色：编辑型展示字体用于章节标题；高可读无衬线用于正文；等宽字体用于提交、版本、数据和证据 ID。
- 结构：细分隔线、编号、边注和留白；避免无意义的圆角卡片堆叠。
- 动效：章节进入、证据栏切换和 brand 示例的非承重动效；支持减少动效。

外壳的视觉强度保持克制，避免让“研究展厅”本身制造虚假的高 SPECTACLE 结论。

## 12. 响应式与可访问性

- 桌面端使用主画布与可折叠证据侧栏。
- 窄屏按单列阅读；证据侧栏变成底部抽屉或章节手风琴。
- `brand`、`product`、`commerce` 使用语义化标签页和方向键导航。
- 所有按钮、筛选、步骤、抽屉和下载操作支持键盘。
- 提供可见焦点、跳过链接和合理的标题层级。
- 状态不只靠颜色表达。
- 图形关系提供文字摘要。
- 尊重 `prefers-reduced-motion`。
- Product 表格和 Commerce 比较表在小屏提供可读的卡片或定义列表表达。

## 13. 错误与空状态

### 13.1 构建期

以下情况使构建失败：

- 缺少固定提交、版本或许可；
- 能力条目没有来源、限制或状态；
- 能力事实的来源 URL 没有固定到研究提交；
- register 示例缺少 Design Read 或三旋钮；
- 机会方向不是六项；
- 使用了未定义状态。

### 13.2 运行时

- 无效章节、register 或步骤参数回退到安全入口，并说明已重置。
- 空筛选结果显示恢复操作，不显示空白画布。
- 决策包生成失败时保留当前视图并提供重试，不显示成功下载。
- 外部来源链接不可用时不推测或替换内容；展厅保留固定引用和边界说明。
- 本地示例中的“升级”“确认”等操作明确显示“演示模式，不会提交”。

首版没有网络加载状态、登录状态或权限状态，因为这些能力不在范围内。

## 14. 测试策略

### 14.1 数据与领域测试

- 固定提交、版本、许可和状态模型一致；
- 所有能力均有来源和限制；
- 三个示例均有 Design Read、三旋钮和真实性说明；
- 六张机会卡字段完整；
- 不存在把解释性演示写成上游产物或已验证实验的表述。

### 14.2 组件测试

- register 标签切换；
- Product 筛选与空结果；
- Commerce 方案和席位计算；
- EvidenceRail 展开与关闭；
- AnalysisStepper 前进、后退和 URL 恢复；
- ScenarioJourney 步骤与决策包导出；
- OpportunityMap 筛选和回链。

### 14.3 浏览器测试

- 桌面和移动端三幕主路径；
- 键盘完成主要交互；
- 深链接恢复章节、register 和步骤；
- 减少动效模式；
- 状态标签和真实性说明持续可见；
- 决策包成功下载；
- 无控制台错误；
- 构建产物可通过静态服务器运行。

浏览器测试结果只描述实际测试的展厅版本、浏览器和视口。

## 15. 完成标准

首版完成需满足：

- 可通过单一命令安装、开发、测试和构建；
- 三幕叙事和顶部范围说明可运行；
- 三个 register 示例均可操作；
- 每个示例均有同步证据侧栏；
- 冻结 brief 的分析链完整；
- SaaS 新功能发布场景可从需求走到产品判断；
- 六个扩展方向均有使用场景、风险和优先级；
- 所有关键声明有来源或明确状态；
- 桌面、移动端、键盘和减少动效路径通过验证；
- 根 README 和第八项目 README 准确列出首版实际实现的模块，同时继续列出未执行的实验和未接入的服务。

## 16. 非目标

- 安装或修改用户本机的 Finesse Skill；
- 复制或改造上游源码与示例资产；
- 调用 AI 实时生成页面或 Design Read；
- 实时读取 GitHub；
- 运行 B1–B5 受控实验；
- 接入真实 detector、浏览器证据平台或审计服务；
- 用户账号、权限、数据库或团队协作；
- 真实支付、套餐升级或业务提交；
- 声称 Finesse 的跨模型效果、性能或商业价值已验证。

## 17. 后续阶段

首版验证可追溯阅读和解释性演示后，再按以下顺序扩展：

1. 为冻结 brief 增加可编辑但仍本地运行的 Brief Router；
2. 接入独立保存的证据记录和 Review Console；
3. 执行 B1–B5 与 A/B/C 受控对照；
4. 接入 Design Model Studio 和 Multi-Register Prototype Lab；
5. 在证据和团队需求成熟后扩展知识库与治理层。

任何后续阶段仍需保持来源、解释性演示、运行时证据和产品构想之间的状态隔离。
