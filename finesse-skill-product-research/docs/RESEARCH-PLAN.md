# Finesse 受控研究计划

## 目的、范围与状态

本计划回答“如何研究并验证 Finesse”。研究对象固定为上游提交 [`ba004b21e14e55385992dff6e345db7108deca78`](https://github.com/mouse-lin/finesse-skill/tree/ba004b21e14e55385992dff6e345db7108deca78) 的 `finesse-ui` `0.12.0`。术语和已知机制以[能力地图](CAPABILITY-MAP.md)为准：Finesse 是设计决策与执行指导 Skill，而非浏览器运行时组件库或自动生成产品的服务。

本文定义的是**尚未执行**的协议、样本和证据口径；不报告分数、截图、运行时间、性能数值或已观察到的产品行为。任何未来结论都必须回填到证据记录，并与固定版本、运行环境和比较组对应。

## 固定实验 brief

五组 brief 覆盖 Finesse 已定义的 register 及其关键分流。每个 brief 的业务事实、内容数据、目标设备、验收任务和实现边界在开跑前冻结；除待测策略外，其余输入保持一致。

| 实验族 | 固定 brief | 主要路由假设 | 必须验证的任务焦点 |
|---|---|---|---|
| B1 | 高辨识度品牌落地页（brand landing page） | `brand` | 人格、品牌 substrate、hero engine 与降级是否可解释且不妨碍主要信息。 |
| B2 | 数据密集型运营仪表盘（operations dashboard） | `product` / read | 信息密度、数据阅读、表格或图表结构与层级是否支持阅读。 |
| B3 | 有真实提交后果的发布工作流（consequential publish workflow） | `product` / operate | 关键操作、确认、错误恢复和提交后果是否清楚。 |
| B4 | 单品 PDP（single-product PDP） | `commerce`，偏 `brand` | 叙事与规格、评价、信任信息的平衡，以及购买路径的清晰度。 |
| B5 | 多商品 PLP（multi-product PLP） | `commerce`，偏 `product` | 筛选、排序、商品网格与较低 SPECTACLE 下的比较效率。 |

这些是待测试的路由假设，不是已验证的输出。尤其是 PDP 与 PLP 的倾向来自上游定义，不能替代支付、库存、风控、税务或合规验证。

## 四阶段协议

### Phase 1 能力审计

**目标：** 固定研究对象，区分“上游已定义的机制”与“仍需实测的效果”。

1. 锁定上游提交、Skill 版本、宿主 Agent 版本、运行环境和测试仓库状态。
2. 阅读主 Skill、关键 references、示例与 `detect.mjs`，把 `register` 路由、SOUL / SPECTACLE / DENSITY、三条设计路线、命令式迭代、设计模型和质量门禁映射到实验变量。
3. 为 B1–B5 建立同一份 brief 基线，明确允许加载的 references、不得变化的业务内容和验收任务。
4. 产出能力—假设清单与空白证据记录；此阶段不把文档中的要求称为运行时效果。

### Phase 2 受控实验

**目标：** 在可复现的条件下，让每个 brief 依其预设 register 走完整设计决策流程。

1. 对每个实验先记录原始 brief、Design Read、三旋钮和加载的 references，再启动生成或改造工作。
2. 保持模型/宿主版本、起始代码、内容数据、屏幕尺寸、网络与测试步骤一致；每次仅改变预先登记的策略变量。
3. 保留产物路径、源码版本、detector 原始结果及浏览器检查所需的可复现步骤。
4. 对 B3 特别记录提交前确认、失败提示和恢复路径；对 B4/B5 特别记录购物任务的完成步骤。它们是计划检查点，并非当前已观察到的行为。

### Phase 3 对照验证

**目标：** 将可归因的差异与非可归因的主观偏好区分开。

对每个固定 brief 建立三组对照：

| 组别 | 策略 | 用途 |
|---|---|---|
| A | 无 Skill 的同等业务 brief | 建立未受 Finesse 指引的基线。 |
| B | 原版 Finesse | 检验固定提交所定义的路由、旋钮、references 与检查流程。 |
| C | 调整后策略 | 在明确记录唯一改动后，检验假设中的改进或修正。 |

三组必须使用相同的功能范围、内容数据、验收任务与浏览器检查脚本；若无法保持一致，记录为混杂因素，不做强比较结论。由至少两名评审独立完成盲化的人工评审，并记录分歧与裁决理由。静态 detector、浏览器证据和人工判断分别保存，不能相互替代。

### Phase 4 产品归纳

**目标：** 仅把经证据支持且边界清楚的机制沉淀为产品机会。

1. 汇总各实验记录，按评价维度、register、失败模式和修正动作归类。
2. 将“已证据支持”“证据不足”“不支持/需重做”分别标注；不以单个样本推广为通用能力。
3. 把可复用的输入、审计、比较和设计模型机制映射到[产品方向](PRODUCT-DIRECTIONS.md)的机会卡与未来展厅叙事。
4. 任何产品优先级都以此阶段的证据更新；本文所列机会仍是研究假设，不是已上线功能。

## 统一证据记录

每一次运行、重跑或失败尝试均使用一条独立记录，避免把后续修正覆盖原始证据。

| 字段 | 必填内容与记录规则 |
|---|---|
| 实验 ID | 唯一标识，例如实验族、对照组、轮次与日期；不得复用。 |
| 上游提交 | 完整提交哈希、Skill 版本、宿主 Agent/模型和运行环境。 |
| brief | 冻结后的原文、内容数据版本、目标任务及任何已批准的偏离。 |
| Design Read | register 判断、页面任务和判断理由；含不确定性或人工确认。 |
| 三旋钮 | SOUL / SPECTACLE / DENSITY 的 1–10 值、推导理由与改动历史。 |
| 加载的 references | 实际加载的相对路径、版本和加载目的；未加载也要明确记录。 |
| 产物路径 | 源码提交、构建产物、可访问地址或本地路径，以及复现步骤。 |
| detector 结果 | 完整命令、原始输出、退出码、`--strict` 使用情况和人工处置。 |
| 浏览器证据 | 截图、录屏或可复现交互步骤、视口、控制台与网络异常；缺失时标为缺失。 |
| 无障碍 / 响应式 / 性能 | 所用工具、场景、设备/视口、原始结果与未覆盖项；不以推测补齐。 |
| 人工评审 | 评审者、盲化条件、八项维度判断、分歧、理由和裁决。 |
| 失败与修正 | 失败模式、影响范围、假设原因、修正命令或策略、是否重跑。 |
| 结论状态 | `待执行`、`证据收集中`、`已证据支持`、`证据不足` 或 `不支持/需重做`；关联证据 ID。 |

## 固定评价维度

| 维度 | 要回答的问题 | 可接受证据 |
|---|---|---|
| 方向匹配 | 输出是否与 brief 的 register、Design Read 和业务任务相符？ | 路由记录、任务走查、人工评审。 |
| 差异化 | 品牌表达或产品结构是否避免无理由的默认模板化？ | 产物对照、机制说明、人工评审。 |
| 任务可完成性 | 用户能否完成阅读、筛选、发布或购买等冻结任务？ | 浏览器交互证据、任务走查、失败记录。 |
| 一致性 | 多页面或多次迭代是否与设计模型、锁定的 substrate 和规则一致？ | `PRODUCT.md` / `design-model.yaml` 对照、diff、人工评审。 |
| 无障碍 | 键盘、语义、对比度、焦点、动效降级等是否经实际检查？ | 浏览器与辅助工具结果、人工复核。 |
| 性能 | 关键场景在目标设备与网络条件下是否满足预先声明的预算？ | 浏览器性能证据、环境与原始测量。 |
| 可解释性 | 是否能追溯每项关键决策到 brief、Design Read、旋钮、reference 或修正？ | 完整证据记录与审计链。 |
| 迭代成本 | 达到验收或修正失败模式所需的轮次、人工介入与变更范围如何？ | 轮次记录、修正日志和版本 diff。 |

## 证据边界与停止规则

`detector` 是代码模式检查：其 findings、JSON 输出或退出码只能作为静态信号。**静态检测绝不是运行时证据，也不得被写成浏览器渲染、交互、无障碍、响应式、性能或审美已经通过。** 即使 `--strict` 返回成功，也仍须保留相应的浏览器证据；没有浏览器证据时，相关结论状态必须为“证据不足”或“待执行”。

高 SPECTACLE 方案还必须有真实视觉引擎、降级策略和目标设备的检查；未记录 `prefers-reduced-motion`、窄屏和中端设备情形时，不能宣称体验完整。任何未复现的错误、未冻结的输入、无法比较的对照组或缺少原始输出的结果，均停止归纳并进入“失败与修正”。
