# Finesse 研究展厅计划

## 范围与诚实状态

本文件指定一个**未来**的 Finesse 研究展厅：它应帮助访客阅读已知能力、编排受控实验、区分证据，并把研究结论谨慎映射为产品机会。它不是 Finesse 的运行时组件库，也不替代需求研究、浏览器测试或人工评审。

本次交付只有研究文档；**尚未实现**展厅代码、页面、交互、数据接入、截图、部署、性能结果或验证结论。下文的屏幕、控件和数据流均为计划，不能据此声称任何功能已经可用。

## 状态模型

展厅中的每一条机制、证据和机会都应有可见状态，且状态的含义不得混用：

| 标签 | 含义 | 当前交付中的使用边界 |
|---|---|---|
| 上游已实现 | 固定上游提交的 Skill 已定义该机制。 | 只能链接到[能力地图](CAPABILITY-MAP.md)中的可追溯事实；不表示本项目实现或验证了展厅。 |
| 本项目已验证 | 本项目以冻结输入、原始记录和相应证据完成了验证。 | 预留标签；本次交付没有可标为此状态的展厅功能或实验结论。 |
| 计划验证 | [研究计划](RESEARCH-PLAN.md)已定义协议，但尚待执行或补齐证据。 | 用于 B1–B5、三路线、三组对照（A/B/C）及尚未取得的浏览器、无障碍、性能和人工评审证据。 |
| 产品构想 | [产品方向](PRODUCT-DIRECTIONS.md)中的机会排序或未来产品假设。 | 不表示已上线功能、市场结论或团队服务承诺。 |
| 尚未实现 | 尚未编写或接入的展厅能力。 | 本交付的全部展厅界面、交互和数据流均为此状态。 |

## 目标与入口

推荐将展厅做成“设计决策与审计工作台”的可读入口：Design Brief Router 负责把冻结 brief 及其 register、Design Read 和三旋钮变为可审阅输入；Design Model Studio 提供生成前约束；AI Design Review Console 汇合静态、浏览器和人工证据。Multi-Register Prototype Lab 服务受控对照，Pattern Knowledge Base 与 Team Governance Layer 仅在证据和团队需求成熟后扩展。

进入展厅时，访客首先看到范围提示与当前状态筛选，明确“上游已实现”不等于“本项目已验证”，而“计划验证”和“产品构想”都不是结果陈述。

## 五个展区

### 1. 能力总览

| 项目 | 计划规格 |
|---|---|
| 用户问题 | 固定版本的 Finesse 已定义了什么机制，它的边界又在哪里？ |
| 屏幕内容 | 能力地图的能力组：register 路由、SOUL / SPECTACLE / DENSITY、brand/product/commerce 路线、命令式迭代、设计模型、质量门禁和多 Agent 适配；每项附来源、限制与状态。 |
| 交互 | 按 register、能力组或状态筛选；展开来源与限制；跳转至对应研究变量。 |
| 所需数据 | 固定上游提交、Skill 版本、能力地图条目、来源链接、限制和状态标签。 |
| 空/错误状态 | 没有固定提交或能力条目时显示“缺少可追溯能力事实”；来源不可读时保留条目并标注“来源读取失败”，不以推测补齐。 |
| 真实状态标签 | 上游已实现；尚未实现。 |
| 声称功能可用前所需证明 | 上游链接与固定提交可复查；展示内容逐项与能力地图一致；筛选和来源跳转经浏览器、键盘和窄屏检查，并保留原始记录。 |

### 2. 决策实验室

| 项目 | 计划规格 |
|---|---|
| 用户问题 | 一个冻结 brief 应如何形成可确认的 register、Design Read、三旋钮和 references 决策包？ |
| 屏幕内容 | B1–B5 brief 列表、冻结输入、候选 register、Design Read、SOUL / SPECTACLE / DENSITY、reference 清单、不确定性和人工确认记录。 |
| 交互 | 选择实验族；审阅或修订候选决策；确认后导出带版本和理由的决策包，供实验记录使用。 |
| 所需数据 | 冻结 brief、内容数据版本、目标任务、上游版本、Design Read、旋钮、references、人工确认和证据 ID。 |
| 空/错误状态 | 缺少冻结 brief 时禁止导出并说明“输入尚未冻结”；路由有歧义时要求人工确认；保存失败时保留未提交草稿并显示失败原因。 |
| 真实状态标签 | 计划验证；尚未实现。 |
| 声称功能可用前所需证明 | B1–B5 的输入冻结与变更历史可复现；导出的决策包可追溯到输入和理由；确认、错误恢复和导出在浏览器中实际走查。 |

### 3. 三路线对照

| 项目 | 计划规格 |
|---|---|
| 用户问题 | 同一业务 brief 在 `brand`、`product`、`commerce` 三条 register 路线下会形成哪些不同产物；在每条路线内，三组对照（A：无 Skill、B：原版 Finesse、C：调整后策略）又有哪些可归因差异？ |
| 屏幕内容 | 以 `brand` / `product` / `commerce` 为主轴并列三条路线，分别展示 register 决策、输入版本、产物路径、任务走查、detector 原始输出、浏览器证据、人工评审和混杂因素；三组对照（A/B/C）作为每条路线内的次级维度或审计筛选。 |
| 交互 | 锁定一个业务 brief、验收任务与评价维度，先并列查看三路线；再在路线内切换或筛选三组对照（A/B/C），展开唯一策略差异；记录“不可比较”原因，不输出强比较结论。 |
| 所需数据 | 三路线的冻结 brief、register 决策与相同验收任务；每条路线内三组对照（A/B/C）的源码与产物版本、策略变量、浏览器证据、detector 原始输出、两名以上评审的盲化记录、分歧与裁决。 |
| 空/错误状态 | 任一路线缺少相同业务 brief、功能范围、内容数据或任务脚本时显示“三路线不可比较”；任一三组对照记录不完整时显示“对照证据缺失”；缺浏览器证据时明确为“证据不足”。 |
| 真实状态标签 | 计划验证；尚未实现。 |
| 声称功能可用前所需证明 | 三路线均能从同一业务 brief 在固定条件下重跑；每条路线内的三组对照（A/B/C）只改变预登记策略变量；任务、无障碍、响应式和性能结论均有原始浏览器或工具证据，不能由静态 detector 替代。 |

### 4. 审计台

| 项目 | 计划规格 |
|---|---|
| 用户问题 | 一项设计或生成产物有哪些静态、运行时和人工证据，哪些风险仍未覆盖？ |
| 屏幕内容 | 产物摘要、detector 原始输出与退出码、浏览器截图/步骤、控制台与网络异常、八项评价维度、失败与修正、证据状态和人工裁决。 |
| 交互 | 按证据类型和严重度过滤；关联证据 ID；创建修正任务或标记缺口；在静态、运行时和人工判断之间切换，不合并其效力。 |
| 所需数据 | 实验 ID、产物路径、完整命令与原始输出、视口/设备、浏览器证据、无障碍/响应式/性能检查、评审记录、修正日志和权限信息。 |
| 空/错误状态 | 无 detector 输出时显示“静态证据缺失”；无浏览器证据时显示“运行时证据缺失”；上传或读取失败时显示具体文件/权限错误，不显示“通过”。 |
| 真实状态标签 | 计划验证；产品构想；尚未实现。 |
| 声称功能可用前所需证明 | 静态信号、浏览器结果和人工评审均能独立追溯；`--strict` 成功不被写成运行时通过；错误恢复、权限和审计留痕经真实工作流验证。 |

### 5. 机会地图

| 项目 | 计划规格 |
|---|---|
| 用户问题 | 经证据支持后，哪些机制值得进入产品主线，哪些仍只是待验证构想？ |
| 屏幕内容 | 六张机会卡：Design Brief Router、AI Design Review Console、Design Model Studio、Multi-Register Prototype Lab、Pattern Knowledge Base、Team Governance Layer；显示价值/成本、优先级、证据状态、风险和主线位置。 |
| 交互 | 按优先级、证据状态和模块筛选；从机会卡回链到实验与审计记录；比较主线与后续扩展的依赖。 |
| 所需数据 | 产品方向卡、优先级、研究证据 ID、失败模式、成本假设、依赖关系、责任人与更新时间。 |
| 空/错误状态 | 没有证据关联时显示“机会尚无验证证据”；缺少更新时间或责任人时标出治理缺口，不自动提高优先级。 |
| 真实状态标签 | 产品构想；计划验证；尚未实现。 |
| 声称功能可用前所需证明 | 每张卡可回链到受控研究的原始记录；优先级变动有理由与版本；筛选、回链和依赖说明经无障碍与响应式检查。 |

## 推荐信息架构

桌面端使用三栏工作台：左侧为实验与状态导航；中间为当前展区的主内容；右侧为证据、来源、限制和当前筛选条件。全局顶部保留固定研究版本、状态图例和“计划展厅，尚未实现”的范围提示。五个展区应按“能力总览 → 决策实验室 → 三路线对照 → 审计台 → 机会地图”顺序连接；每个下游结论必须能回到上游输入与证据。

移动端折叠为单列：顶部只保留当前实验、状态标签和范围提示；左、右栏改为可展开的“导航”和“证据/来源”抽屉。对照区不得把三路线挤成不可读卡片，应先按 `brand` / `product` / `commerce` 分段切换，再用三组对照（A/B/C）筛选当前路线内的策略记录，并持续显示相同输入和可比性状态。任何筛选、导出或修正操作都必须有明确的焦点、返回位置和结果提示。

## 计划数据流

1. 从能力地图载入固定上游版本、机制、来源和限制，供能力总览使用。
2. 从研究计划载入 B1–B5、冻结输入规则、三路线 register 决策、三组对照（A/B/C）、评价维度与证据记录结构，供决策实验室、三路线对照和审计台使用。
3. 将每次运行的原始输入、产物路径、detector 输出、浏览器结果、人工评审和修正日志作为不可覆盖的证据记录保存；后续修正新增记录而非覆盖原记录。
4. 仅当证据满足研究计划的归纳条件时，才把带证据 ID 的结论映射到机会地图；没有浏览器证据的运行时结论保持“计划验证”或“证据不足”。
5. 机会地图将可追溯结论反链回输入、对照和审计，不将排序、静态信号或单个样本展示为通用能力。

## 可访问性与内容要求

- 所有状态不能只靠颜色表达，并要有可读名称、来源和边界说明。
- 对照、筛选、抽屉、导出和修正操作须支持键盘、可见焦点、语义化控件和清晰反馈。
- 数据表与卡片须提供标题、列/行语义和适合小屏的替代表达；图形化关系需有文本摘要。
- 尊重 `prefers-reduced-motion`；若后续引入动效或高 SPECTACLE 视觉引擎，必须提供降级路径并在目标设备上验证。
- 空、加载、失败、权限不足和证据缺失状态必须明确，不能以占位内容、伪造指标或“通过”掩盖缺口。

## 分阶段实施路线图

1. **P0：可追溯阅读。** 实现能力总览、状态图例和研究范围提示，只读取已固定的文档数据；先验证来源、筛选、键盘和窄屏阅读。
2. **P0：决策与审计骨架。** 引入冻结 brief 的决策包、证据记录结构和审计台，但不把静态 detector 结果提升为运行时结论；验证保存、错误恢复和审计留痕。
3. **P1：受控对照。** 为 B1–B5 接入三路线编排，并在每条路线内接入三组对照（A/B/C）；先确保输入、任务与环境可比，再做浏览器、无障碍、性能和人工评审采集。
4. **P1：设计记忆与探索。** 接入 Design Model Studio 和 Multi-Register Prototype Lab，验证版本比较、冲突暴露、人工确认与对照变量控制。
5. **P2：受控知识与团队扩展。** 在有来源、许可、证据和治理机制后，再扩展 Pattern Knowledge Base 与 Team Governance Layer；验证权限、例外、CI 和审计边界。

在任一阶段，未冻结输入、不可比较对照、缺少原始输出或缺少浏览器证据时，应停止归纳并保留缺口状态。没有这些证明，就不能宣称未来展厅“可用”、研究结论“已验证”或体验“已通过”。
