# Finesse 产品机会方向

## 机会判断边界

以下六张卡把[能力地图](CAPABILITY-MAP.md)中已定义的机制转译为待验证的产品机会。它们不表示产品、模型、浏览器审计或团队服务已经实现；尤其 `detector` 只能提供静态信号，截图和浏览器检查仍需按[研究计划](RESEARCH-PLAN.md)取得证据。优先级是研究与最小演示的排序，不是市场或收入预测。

## 1. Design Brief Router

- **目标用户：** 接到含混前端需求、需要先对齐设计语境的设计师、产品经理与 AI 编码助手使用者。
- **要完成的工作：** 将自然语言 brief 结构化为 `brand`、`product` 或 `commerce` 的 register，补充 dashboard/read 与 workflow/operate 区分，并给出可审阅的 Design Read 与三旋钮。
- **继承的 Finesse 能力：** register 路由、SOUL / SPECTACLE / DENSITY、Design Read、按任务选择 references。
- **需要新增的能力：** brief 结构化、歧义追问、置信度与人工确认、路由理由的可追溯存储。
- **最小可演示闭环：** 输入一个冻结 brief → 展示候选 register、Design Read、三旋钮与 references → 用户确认或修订 → 导出可供实验记录使用的决策包。
- **关键风险：** 路由被误解为需求发现或用户研究的替代品；含混 brief 的自动判断会产生错误自信。
- **价值 / 实现成本：** 高价值 / 中等成本；它将生成前的隐性判断变为可检查输入。
- **推荐优先级：** P0，作为产品主线的入口模块。

## 2. AI Design Review Console

- **目标用户：** 需要审阅 AI 生成前端、记录质量门禁和协调人工设计评审的设计负责人、工程负责人及团队审计者。
- **要完成的工作：** 将 detector 结果、浏览器证据、无障碍/响应式/性能检查和人工规则集中为分级审计，而不混淆各类证据的效力。
- **继承的 Finesse 能力：** anti-cheap、preflight、质量门禁、`audit` 命令、静态 detector 与浏览器二次验证的边界。
- **需要新增的能力：** 证据上传与关联、浏览器自动化或接入、规则分级、人工裁决工作流、审计留痕与权限控制。
- **最小可演示闭环：** 选择一个产物 → 载入 detector 原始输出与浏览器截图/步骤 → 人工填写八项评价 → 输出含“静态”或“运行时”标签的审计结论和修正任务。
- **关键风险：** 将静态提示伪装成质量认证，或把主观审美规则错误地硬编码为普适门禁；截图也可能无法覆盖真实交互。
- **价值 / 实现成本：** 很高价值 / 较高成本；它把质量争论变为可追溯证据与待修正项。
- **推荐优先级：** P0，是产品主线的审计核心。

## 3. Design Model Studio

- **目标用户：** 维护多页面产品、希望减少生成漂移的设计系统负责人、前端负责人和项目 owner。
- **要完成的工作：** 可视化生成、比较、审阅并锁定 `PRODUCT.md` 与 `design-model.yaml`，使后续请求可读取一致的设计约束。
- **继承的 Finesse 能力：** `init`、`document`、项目记忆、`PRODUCT.md`、`design-model.yaml` 与 drift 暴露机制。
- **需要新增的能力：** 结构化模型编辑器、版本比较、冲突检测、审批与回滚、与代码或设计系统的受控同步。
- **最小可演示闭环：** 导入一个项目模型 → 并列比较两版字体、配色、substrate 与规则 → 锁定一版 → 让 Brief Router 在新请求中读出冲突与确认项。
- **关键风险：** 误把文档化模型当作设计系统的实时真相；自动同步会放大过期或错误约束。
- **价值 / 实现成本：** 高价值 / 中等成本；它为跨页一致性和审计链提供持久上下文。
- **推荐优先级：** P1，作为主线的设计记忆模块。

## 4. Multi-Register Prototype Lab

- **目标用户：** 需要在产品早期比较表达方向的产品设计师、创意技术人员与研究人员。
- **要完成的工作：** 让同一业务 brief 在 `brand`、`product`、`commerce` 及其 dashboard/workflow、PDP/PLP 分流下形成可比较的候选方案。
- **继承的 Finesse 能力：** register 路由、三旋钮、brand/product/commerce 路线、对应 references 和局部迭代命令。
- **需要新增的能力：** 对照实验编排、输入冻结、并列预览、差异标注、浏览器证据采集和实验记录导出。
- **最小可演示闭环：** 固定一个 brief → 生成三张带 Design Read 的候选卡 → 以同一任务走查比较 → 将选择与理由送入 Review Console 的证据记录。
- **关键风险：** 视觉并列容易诱导只按偏好选方案，忽略任务可完成性、无障碍或性能；不同生成条件会破坏对照。
- **价值 / 实现成本：** 中高价值 / 较高成本；它直接服务 Phase 2–3 的研究，但需要严格控制变量。
- **推荐优先级：** P1，作为主线的实验与探索模块。

## 5. Pattern Knowledge Base

- **目标用户：** 希望让团队检索、复用并质疑设计模式的设计系统团队、研究人员与 AI 工作流维护者。
- **要完成的工作：** 将 persona、palette、hero、workflow、reference 和反例按场景、register、证据状态组织为可检索知识。
- **继承的 Finesse 能力：** brand 的 soul/persona、substrate 与 hero engine；product/workflow 参考；commerce 分流；anti-cheap 和 preflight 规则。
- **需要新增的能力：** 结构化知识摄入、来源与许可记录、检索/筛选、证据等级、反例关联、过期处理与编辑治理。
- **最小可演示闭环：** 录入一个已注明来源的模式与一个反例 → 按 register/任务检索 → 在 Brief Router 的建议中显示其证据状态和适用边界。
- **关键风险：** 把经验性审美偏好固化为规范，或在未经许可时复制第三方素材；过时模式会误导生成。
- **价值 / 实现成本：** 中等价值 / 中等成本；它提升复用与解释，但依赖持续治理和高质量证据。
- **推荐优先级：** P2，先以主线的受控参考库形式出现，再决定是否独立扩展。

## 6. Team Governance Layer

- **目标用户：** 需要将团队设计约束、例外与交付风险纳入工程流程的设计运营、平台团队和治理负责人。
- **要完成的工作：** 将强审美规则转成可配置策略、例外申请和 CI 门禁，并保留规则来源、责任人和证据。
- **继承的 Finesse 能力：** 质量门禁、preflight、detector、`--strict`、设计模型与多 Agent 接入路径。
- **需要新增的能力：** 策略配置、角色与权限、例外审批、CI 集成、审计日志、规则版本化及误报管理。
- **最小可演示闭环：** 配置一条含证据边界的团队规则 → 在一次提交中运行静态检查 → 对 finding 创建例外或修正 → 在 Review Console 留下审批与浏览器验证状态。
- **关键风险：** 把启发式规则变为阻塞式、不可质疑的门禁；静态检查误报、绕过和跨团队权限冲突会损害采纳。
- **价值 / 实现成本：** 高价值 / 高成本；适合有稳定规则和审计需求的团队，而非最初单人验证。
- **推荐优先级：** P2，待主线验证证据与团队需求后进入后续阶段。

## 比较与产品主线

| 方向 | 主要价值 | 成本 | 优先级 | 在主线中的位置 |
|---|---|---:|---|---|
| Design Brief Router | 使生成前决策可解释、可确认 | 中 | P0 | 入口模块。 |
| AI Design Review Console | 汇合静态、浏览器与人工证据 | 较高 | P0 | 审计核心。 |
| Design Model Studio | 锁定跨页设计约束并暴露漂移 | 中 | P1 | 设计记忆模块。 |
| Multi-Register Prototype Lab | 支持受控的方案对照与选择 | 较高 | P1 | 研究/探索模块。 |
| Pattern Knowledge Base | 让模式、反例和边界可检索 | 中 | P2 | 受控参考库，后续可独立。 |
| Team Governance Layer | 将策略、例外和门禁纳入团队流程 | 高 | P2 | 团队扩展阶段。 |

推荐的产品 spine 是**设计决策与审计工作台**。它把 Design Brief Router 的输入路由、Design Model Studio 的生成前约束、AI Design Review Console 的证据审计连成可验证闭环；Multi-Register Prototype Lab 用于研究与探索，Pattern Knowledge Base 作为受控知识模块，Team Governance Layer 则在证据和团队需求成熟后进入后续阶段。这个选择是机会排序，仍需通过受控研究验证。
